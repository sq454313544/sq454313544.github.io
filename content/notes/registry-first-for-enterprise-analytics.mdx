## 问题：为什么不能只靠模型生成查询

自然语言问数最容易被误解成“把问题交给模型，再让模型自己找数据”。这种方式在演示中很快，但在企业分析场景会遇到三个根本问题：指标口径隐含在人的经验里、同一问题可能被映射到不同数据来源、变更后难以知道哪些回答受影响。

模型可以理解表达差异，却不应该成为业务定义的唯一载体。要获得稳定结果，先要把“什么可以问、怎样解释、怎样执行”变成显式资产。

## 核心结论：先注册能力，再编排回答

Registry First 的要点是把指标、维度、明细能力与查询约束收敛到可维护的注册表中。模型的职责从“猜测业务逻辑”转为“识别用户意图、选择已有能力、解释执行结果”。

## 注册表应包含什么

不要把注册表理解成一份静态字段清单。它至少需要描述四类信息：

1. **业务定义**：指标的含义、统计粒度、可用时间口径与允许维度。
2. **能力边界**：哪些问题可以回答、哪些情况应澄清或拒绝。
3. **执行约束**：允许的查询模板、结果规模与权限要求。
4. **变更关系**：定义调整后，需要重新验证的能力、测试和下游消费者。

这让一致性不再依赖某个 Prompt 或某位维护者的记忆，而是可以被审查、测试和迭代的契约。

## 从 Registry 到 Metadata Control Plane

当 Registry 只有少量配置时，文件校验和应用重启通常足够；当指标、维度、明细、Prompt、索引和多个消费者开始独立演进，系统还需要回答“当前运行的是哪个版本”“索引与定义是否一致”“发布失败如何回退”。

元数据控制面并不取代 Registry，而是为它补上版本和运行治理：

1. 从权威业务契约生成确定性的运行时快照，为每项资产分配稳定标识和内容摘要。
2. 在发布前检查定义、引用、执行映射与兼容性，不让严重差异直接进入运行时。
3. 先完成持久化和索引准备，再切换 Active 版本，避免查询命中半发布状态。
4. 检索依赖不可用时，同次请求回退到已验证 Registry；回滚时同步恢复版本、索引与缓存边界。

控制面的价值不是“再建一个元数据库”，而是把发布状态、读写职责和失败恢复变成可执行契约。

## 从需求到上线的变更链路

新增一个指标不应只是在提示词里加一句说明。更可靠的流程是：确认业务定义，更新权威契约，生成运行时快照，校验执行映射，发布新版本与索引，加入评测样本，再观察发布后的异常与追问。每一步都能追溯，出错时也能定位是定义、派生、检索、执行还是解释的问题。

## 为什么采用渐进认证

一次性认证所有数据资产通常成本过高，也容易让团队把精力放在低价值字段上。更实际的方式是先覆盖高频、口径敏感和风险较高的能力，再根据受控使用中的真实问题补充定义。

渐进不等于放松治理：未确认项进入待确认清单，不能直接修改正式 Registry；确认后仍需先更新权威契约，再派生运行时版本。这样既避免“大而全”的长期冻结，也避免使用反馈绕过事实源直接改变查询结果。

## 为什么新增指标通常不需要修改 Prompt

关键不在于“把所有指标写进提示词”，而在于把三类变化拆开：

- **稳定行为**放在 Prompt：先检索能力、信息不足时澄清、执行前校验、结果中说明口径。
- **动态知识**放在 Registry：指标定义、别名、可用维度、时间口径、权限与生命周期。
- **确定性动作**放在 Tool：读取元数据、生成受控查询计划、执行和审计。

运行时由 Metadata MCP 按当前问题检索少量候选，再把结构化结果交给模型。新增常规指标时，变化发生在 Registry、测试样本和索引中；模型仍遵循同一套行为协议，不需要在静态 Prompt 里追加一段新知识。

“无需修改 Prompt”并不等于“永远零代码”。如果新指标需要新的计算模式、数据源协议或权限模型，就应扩展执行能力和契约；Registry 只适合承载已经被通用执行器支持的变化。

## Metadata MCP 如何缩小幻觉空间

Metadata MCP 不是让模型凭空知道更多，而是把它可选择的范围缩小到可验证集合：

1. 根据用户表达检索已注册的指标、维度与明细能力。
2. 只返回与当前问题相关的候选及必要字段，避免把完整数据字典塞进上下文。
3. 要求模型输出结构化能力标识和参数，再用 Registry 二次校验。

因此，模型仍可能选错候选，却难以编造一个不存在的指标并直接执行。系统也能区分“没有匹配”“存在多个候选”和“参数不合法”，分别进入拒答、澄清或修正流程。

## 配置化扩展的边界

Registry First 可以理解为“把变化的策略配置化，把稳定的执行机制留在代码中”。判断一项变化放在哪里，可以使用一个简单标准：

| 变化 | 优先位置 |
|---|---|
| 指标名称、说明、别名和生命周期 | 权威契约 / Registry |
| 允许维度、时间口径和权限声明 | 权威契约 / Registry |
| 资产版本、发布状态、索引别名和回退 | Metadata Control Plane |
| 候选检索、参数校验和审计协议 | Tool / 服务代码 |
| 新的计算范式或数据源连接方式 | 代码与接口契约 |
| 澄清、拒答和调用顺序 | Prompt / 工作流 |

这种边界避免两个极端：既不把业务知识重新硬编码进应用，也不把无法验证的任意逻辑伪装成配置。

## 常见追问

### 用户说法和标准名称不一致怎么办？

让模型负责识别候选能力，但由注册表决定最终可用范围。当候选不唯一时，应要求澄清或展示可选解释，而不是悄悄选择一个看似合理的答案。

### 注册表会不会维护成本太高？

维护成本确实存在，但它取代的是分散在报表、临时查询、口头规则与 Prompt 中的隐性成本。优先覆盖高频且口径敏感的能力，随着使用价值逐步扩展，而不是一开始试图登记所有数据。

### 如何验证注册表是否可靠？

为关键能力建立问题集、期望路由和结果校验，并在定义、派生逻辑、索引或执行能力变更时重新运行。高风险能力还应检查权威引用、资产标识、发布状态和回退路径。真实使用异常可以脱敏后进入回归集，但不能自动改写正式定义。

### Registry 更新后如何避免旧缓存？

缓存键应包含 Active Registry 版本或内容摘要；新版本发布后主动失效相关元数据与查询计划。回滚时也要恢复与旧版本匹配的索引别名和缓存边界，避免“配置已经回滚，运行时仍使用新候选”的混合状态。
