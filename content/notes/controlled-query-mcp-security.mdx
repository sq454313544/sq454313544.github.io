## 问题：为什么不让模型直接查询数据

模型生成的内容具有不确定性，而数据查询同时涉及权限、资源消耗和业务解释。即使模型“看起来知道”要查询什么，也不能因此获得任意执行权限。可靠的设计应当把模型放在理解和编排的位置，把数据访问收敛到唯一的受控入口。

## 核心结论：安全不是单点校验

Query MCP 的价值不在于增加一个接口，而在于把安全策略放到每次执行都必须经过的关口。任何单一规则都可能被绕过；多层约束共同决定一次请求是否允许执行、在什么范围内执行、如何记录结果。

## 五类防线

### 1. 能力与权限

先判断当前用户是否可以调用某类能力，再根据授权范围约束可见数据。权限上下文应由可信身份来源构建，而不是由模型或用户输入自行声明。

### 2. 参数与语法

查询计划中的参数必须遵循预设类型与范围。对语法树进行校验，可以识别不应出现的语句和结构；允许的能力、字段与操作同样需要白名单约束。

### 3. 行级范围与结果规模

授权范围应在执行层统一注入，而非依赖调用者自觉传递。对返回行数、聚合粒度和超时设置上限，既控制风险，也避免一次请求占用过多资源。

### 4. 只读执行

执行身份只保留完成查询所需的最小权限。模型不会获得数据源账号，也不负责拼接可执行语句。

### 5. 审计与失败处理

记录请求能力、权限范围、校验结果和执行状态，便于事后定位。校验失败时返回可理解的拒绝原因或澄清建议，而不是尝试“猜一个替代查询”。

## 常见追问

### 为什么数据库权限不足以解决所有问题？

数据库权限是底线，但它不知道一次自然语言请求对应的业务能力、参数意图和产品规则。应用层控制补足了能力可见性、参数验证、返回规模和审计语义。

### 如何应对提示词注入？

不要把安全决策交给提示词。即使模型被诱导改变输出，受控执行层仍需独立验证能力、权限、参数和语法；不满足规则的请求不能进入执行。

### 审计记录什么才有用？

记录足以复现决策过程的最小信息，例如能力标识、请求时间、校验状态、授权范围摘要和结果规模。避免默认记录用户的敏感原始内容或真实业务结果。
