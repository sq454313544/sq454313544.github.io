## 先定义边界，而不是先堆组件

企业智能问数通常同时面对表达不确定、知识变化、权限控制、数据执行和运行恢复等问题。架构的关键不是使用多少模型或工具，而是让每一层只承担适合它的职责：入口适配协议，Kernel 管理生命周期，Plugin 编排业务，Capability 提供原子能力，模型理解问题，MCP 收敛执行边界，元数据控制面管理可发布知识。

一条稳定的依赖方向是 `Capability → Registry → Plugin → Kernel`。上层可以组合下层能力，下层不能反向依赖具体业务编排；任何新增入口都复用同一权限、会话和执行契约。

### Gateway：适配入口协议

Gateway 处理 HTTP、SSE 或消息平台协议，生成请求关联标识并把可信身份上下文交给 Kernel。它不判断业务指标，也不直接调用数据库。

### Kernel：管理稳定生命周期

Kernel 负责会话、权限、功能开关、Plugin 管理和公共运行约束。业务判断留在 Plugin，避免每新增一个场景都修改系统生命周期。

### Plugin 与 Capability：分开编排和原子能力

Plugin 把一次业务请求编排成检索、查询、解释或导出步骤；Capability 提供无状态、可复用的原子动作。Plugin 不直接访问数据库或 Redis，也不调用其他 Plugin，减少隐式依赖和循环调用。

### LangGraph：管理状态与分支

工作流需要处理澄清、路由、工具调用、失败恢复和追问。图结构适合显式表达状态与分支：每个节点只处理一类职责，节点之间传递必要状态，而不是把所有逻辑塞进单轮提示词。

### Metadata MCP：把知识提供给模型

Metadata MCP 不直接执行查询，它负责把注册表中的可用能力转化为模型可理解的说明。这样业务定义能够独立演进，模型上下文也可以按问题按需提供，而非写死在 Prompt 中。

### Query MCP：把执行收敛到唯一入口

Query MCP 接收经过能力匹配的请求，完成权限、参数、语法和结果规模校验，再调用确定性执行能力。它与 Metadata MCP 分离，避免“知道数据”天然等于“可以执行数据操作”。

### Export MCP：把结果交付与查询分离

导出使用已经授权且仍有效的结果集，独立检查身份、行数、有效期和下载权限。这样“能够查询”不会自动扩大为“能够长期保存或转发结果”。

### Metadata Control Plane：让知识可发布、可回退

权威数据契约先生成稳定的运行时快照，再完成持久化、索引和 Active 版本切换。索引不可用时回退到已验证 Registry；严重契约差异则阻止新基线推进，而不是让半发布版本继续服务。

## 一次请求中三者如何协同

三者不是平级堆叠的组件，而是一条职责清晰的信息加工链：

1. Gateway 接收请求，生成关联标识并交付可信用户上下文。
2. Kernel 恢复会话、应用权限和功能开关，选择业务 Plugin。
3. LangGraph 根据状态判断需要回答、检索、澄清、拒绝还是执行。
4. Metadata MCP 从当前 Active Registry 检索可见的能力候选。
5. LangGraph 把候选与会话状态合并，选择能力或请求澄清。
6. Query MCP 校验结构化参数、权限、语法和预算，再调用受控 Capability。
7. Export MCP 只在用户明确请求且结果仍有效时生成授权文件。
8. LangGraph 根据执行状态生成解释、建议或可恢复的失败反馈，追踪链记录必要状态。

Registry 定义“系统知道什么”，Capability 定义“系统有哪些原子能力”，MCP 决定“能力如何被安全调用”，Plugin 决定“业务如何组合能力”，LangGraph 决定“此刻应走哪一步”。任何一层都不应越权代替其他层。

## 为什么不是普通 Prompt Chain

线性 Chain 适合步骤固定、失败后可以整体重跑的任务；问数流程往往包含分支、追问和局部恢复。选择图工作流，主要是为了显式管理四类复杂性：

| 复杂性 | 图工作流的处理方式 |
|---|---|
| 结构化状态 | 保存能力候选、权限摘要、参数、执行状态与重试原因 |
| 条件路由 | 在回答、澄清、拒绝和执行之间选择分支 |
| 局部重试 | 只重跑失败节点，不重复已经确认的意图与权限判断 |
| 多轮追问 | 从检查点恢复已确认上下文，只增量修改当前条件 |

代价也很明确：状态类型、节点输入输出和循环条件必须被严格定义。流程较短且没有分支时，普通函数或简单 Chain 反而更容易维护。

## 检索与确定性执行如何配合

检索适合解决“有哪些已知能力、哪些说明与当前问题相关”；确定性执行适合解决“在已确认边界内如何得到结果”。把两者混为一谈，容易让检索内容被误当成执行指令，或让模型在信息不足时自行补全规则。

增强检索也必须能够降级。语义索引、外部模型、预热或审计条件不满足时，可以回退到经过验证的关键词候选；不能为了提高召回而绕过权限、类型约束或 Active Registry 版本。质量收益、尾延迟和错误候选需要在同一评测门中衡量。

## 失败降级与可观测性

系统应把失败看作正常分支：能力不匹配时请求澄清，权限不足时给出可理解的边界说明，执行异常时保留可追溯状态并避免重复提交。入口消息需要幂等去重，长任务需要进度心跳和可查询状态，并发、查询、分页、导出和重试都要有预算。

离线评测、确定性回放、自动化测试和真实 Pilot 样本回答的是不同问题，不能互相替代。运行日志和人工反馈共同驱动后续改进，但公开文章只描述方法，不公开用户请求或业务数据。

重试需要有明确范围和预算：检索无结果可以换检索策略，参数校验失败应回到参数修正，执行超时可以建议缩小范围；权限拒绝则不应重试。循环必须设置终止条件，防止工作流把同一个错误不断送回模型。

## 常见追问

### 为什么需要 RAG？

RAG 适合检索说明、示例和能力元数据，但不能替代口径契约或权限校验。它提供相关上下文，最终选择和执行仍要经过受控流程。

### 如何避免工作流越来越复杂？

先定义稳定的输入、输出和失败状态，再让节点按职责拆分。高频流程保持短链路，低频或高风险分支通过明确的澄清与人工处理入口降级。

### 如何评估系统是否变好？

除回答文本外，还要观察能力路由是否正确、受控执行是否符合预期、失败是否被安全处理，以及变更后关键样本是否回归。评测集应随真实问题持续补充和去敏。

### 哪些场景需要人工介入？

高风险数据申请、业务口径冲突和连续多次无法消歧的请求，适合转入人工确认。Human in the Loop 应是明确的状态与权限边界，而不是任何失败后的默认兜底。

### MCP 调用失败后能否换一个相近能力？

只有在用户明确同意且结果中清楚标注口径变化时才可以。静默替换会把基础设施故障变成业务答案错误，通常比直接说明暂时无法完成更危险。
