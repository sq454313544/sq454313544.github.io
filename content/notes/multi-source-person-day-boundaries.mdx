## 问题背景

经营看板里有一条「人员过程数据追踪」线：把通话记录、工作手机日报、回款数据等多个来源，按「日期 × 人员」聚合成人日粒度，再写入智能表格。

这类汇总看起来只是 `GROUP BY 人员, 日期`，实际每一步都有边界条件。以下三类是实际踩到并留下记录的。

## 一、汇总行不是个人行的算术和

工作手机系统的日报表里，**每人每天一行，另外还有一行"全所汇总"**。最初的直觉是：汇总行不就是所有人加起来吗？实测不是：

- 有 4 个接通率类字段是**比率**，不可加；
- 有 5 个时长字段按**分钟**取整，逐人相加与汇总行不相等。

```sql
-- 错误：把汇总行当普通行一起聚合
SELECT ds, SUM(connect_cnt) FROM yunke_report_daily GROUP BY ds;

-- 正确：先剔除汇总行，汇总口径单独取
SELECT ds, SUM(connect_cnt) FROM yunke_report_daily
WHERE is_summary = 0 GROUP BY ds;
```

**约束**：明细表必须带 `is_summary` 标记位，并且**下游汇总一律先过滤**。这条约束如果不写进数据契约，下一个人接手时必然会再加一次汇总行。

另外两个同源坑：

- 导出文件的表头有 4 列与接口字段 `name` **不同名**；
- 导出列的**顺序由提交时的 `index` 参数决定**，不能按位置取值。

## 二、坐席号跨系统会指向不同的人

人日汇总需要把各来源的人员维度对齐。最初的想法是直接用坐席工号做主键，实测发现**工号会复用**：

```text
同一工号，在工作手机系统资料里指向 A，在企业微信实名里指向 B —— 不同的人
```

同一个工号在不同资料里指向不同的人。如果直接用工号对齐，两个来源的人日数据会被错误地合并到一行。

处置口径定为两条：

1. **人名一律取企业微信实名**，不从坐席号、也不从坐席串截取；
2. 人员主数据维护**工号 × 人名**映射表，映射缺失时**停止汇总并报告**，不猜；
3. 展示名做归一（去掉 `姓名(姓名)` 这类重复），同时**保留原始姓名列**以便回溯。

```text
✅ 工号 → 实名映射表（人工确认）→ 人员维度
❌ 工号 → 从坐席串里截取一个名字
❌ 姓名 → 作为跨系统主键
```

**约束**：跨源聚合的人员键必须来自**人工确认的映射表**，而不是任何单一来源的自述字段。

## 三、话单是"一次呼叫尝试一行"

外呼系统的话单表，一行代表**一次呼叫尝试**，不是一个人、也不是一个任务。重呼会产生多行。所以：

- `COUNT(*)` 是呼叫尝试数，不是接通数；
- 也没有"每任务一行"这种天然粒度，需要显式聚合。

实测对账关系如下（以任务为粒度）：

| 指标 | 与话单的关系 | 实测 |
|---|---|---|
| `no_answer_count` | = `COUNT(漏接)` | 109 / 109 一致 |
| `call_connect` | ≈ `COUNT(接通)` | 108 / 109 一致 |
| `called_count` | ≈ `COUNT(DISTINCT 被叫号码)` | 107 / 109 一致 |
| `no_call_connect` | **小于** `COUNT(未接通)` | 关系不成立 |

最后一行是关键：**接口自带字段与"用明细算出来"之间并非处处等价**。所以不能假设"接口字段 = 明细聚合"，必须逐字段建立并验证对账关系。

## 四、一个更隐蔽的边界：同一份数据的两种载体

外呼系统还有个「下载」按钮，导出的是**同一份数据的另一种载体**。最初按"新增数据源"处理，实测后改判：

- 实测任务 44 与 JSON 话单都是 1,124 行且**逐行一致**；
- 真正新增的只有 **3 列**：呼叫唯一标识、呼叫发起时刻、挂断时刻——补上了原来算不了的"拨打时段与持续时长"；
- 另外 9 列与 JSON 逐值等价或恒为常量，**不重复入库**，只保留表头核对与前提失效报警。

**约束**：新增来源前先做**逐行等价性验证**。同一数据的第二种载体不等于第二个数据源；只把"真正新增的字段"接进来，避免同一份数据被算两次。

同时这类载体有**覆盖度差异**：该导出只在任务状态为「进行中／已完成」时可下载，111 个任务里 61 个下不了，因此两张表行数不等是**预期内的**，需要有明确说明，否则会被当成缺失。

## 五、多源采集的通用检查清单

1. **每个来源的粒度先写清楚**：一行代表什么（人日 / 一次呼叫 / 一个任务 / 一次快照）。
2. **汇总行、合计行必须有标记位**，下游一律先过滤。
3. **比率与时长字段不可加**，汇总口径要么取源侧汇总行，要么按定义重算。
4. **跨源人员键取人工确认的映射表**，映射缺失即停止，不猜。
5. **接口字段与明细聚合的关系逐字段对账**，不假设等价。
6. **同一数据的多载体先验证等价性**，只接真正新增的字段。
7. **覆盖度差异要写成显式说明**（哪些任务取不到、为什么），否则会被误判为缺失。
8. **快照来源优先 append**：智能表格这类没有历史版本能力的数据源，覆盖写会永久丢掉"某人何时在名单"。

> 案例来自企业微信经营看板人员维度与外部来源接入的真实实施记录，已去掉内部库表名、工号、真实姓名与业务数值，仅保留方法与判据。
