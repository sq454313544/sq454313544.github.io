## 问题：Planner 优化到底在优化什么

Planner 的职责不是写出一段更长的推理，而是把用户目标转换成可验证、可执行、成本可控的步骤。常见瓶颈包括候选检索不准、简单问题走了过长链路、失败后盲目重试、多指标串行执行，以及每轮对话都重新规划。

优化前应先用评测和运行数据确认瓶颈。如果缺少基线，只凭感觉增加缓存、模型或分支，往往会让工作流更难解释。

## 核心原则

**能用确定性规则解决的问题，不交给模型；能安全复用的计划，不重复规划。**

这并不是追求“模型调用越少越好”，而是把模型用在真正需要语义判断和任务分解的位置，把规则、校验、缓存一致性和执行安全交给确定性系统。

## 六个优化方向

### 1. 查询改写：先规范化，再检索

先用词典、日期解析和实体映射处理稳定规则，例如同义词、缩写和相对时间。只有在表达高度模糊时，才使用模型生成候选改写。

改写结果要保留原始问题，并限制扩展范围。无约束扩展可能提高召回，却把不相关能力一起带入候选集。

### 2. 工具选择：先过滤，再判断

使用分层选择减少无效上下文：

1. 根据权限、内容类型和 Registry 状态做硬过滤。
2. 通过检索得到少量候选。
3. 候选唯一时走确定性短路；候选相近时交给模型判断或请求澄清。

高频且规则明确的问题可以建立受测试保护的快速路径，但不能绕过权限、参数和执行校验。

### 3. 多步规划：只在任务确实可分解时启用

多指标比较、先检索后明细、跨步骤分析适合拆成任务图。相互独立的查询可以并行，有依赖关系的任务必须显式传递结构化结果。

不要为了展示 Agent 能力把单指标查询也拆成多步。每增加一个节点，就增加一次失败、延迟和观测成本。

### 4. 重试：按错误类型决定下一步

重试前先分类：

- 临时网络或服务错误：在预算内重试相同调用。
- 参数校验失败：回到参数修正，不重复意图识别。
- 候选不明确：重新检索或请求澄清。
- 权限拒绝：立即终止，不得重试或降级绕过。
- 业务口径不可用：说明边界，不静默替换相似指标。

重试需要次数、时间和资源预算，并记录每次失败原因，避免循环只是在重复同一错误。

### 5. 计划缓存：复用“怎么查”，不缓存“查到什么”

查询计划缓存保存能力标识、参数结构和工作流路径，执行时仍重新校验权限、时间和 Registry 版本，并重新获取业务结果。

缓存键至少考虑规范化问题、能力版本和影响计划的上下文。涉及用户权限的参数不能跨身份复用；Registry、权限规则或工作流升级后，相关缓存必须失效。

### 6. 成本控制：预算也是规划输入

为不同复杂度任务设置调用步数、延迟和资源预算。接近预算时，可以减少非必要润色、暂停低优先级分析或请求用户缩小范围，但不能降低权限和结果正确性。

模型分层路由应建立在真实评测上。更便宜的模型只有在工具选择、参数和端到端质量保持达标时，才算真正降低成本。

## 如何安排优化优先级

建议按“证据充分、改动可回滚、收益可测量”的顺序推进：

1. 建立 Planner 基线：候选质量、调用步数、失败类型、延迟和成本。
2. 优先加入确定性规范化、错误分类和终止条件。
3. 对高频稳定路径试点计划缓存，并验证失效策略。
4. 再评估多指标并行、模型分层和更复杂的自动规划。

每项优化都应有对照评测。只降低调用次数却提高误选率，或只降低平均延迟却放大尾部失败，都不应视为成功。

## 一个可验证的优化流程

以“比较某个时间段内两个已注册指标”为例：

1. 解析时间表达并做权限过滤。
2. 检查两个指标是否命中有效计划缓存。
3. 对未命中的部分检索候选，必要时一次性澄清。
4. 将两个独立查询组成并行任务，分别经过受控执行。
5. 校验两边结果的时间口径和维度是否可比较。
6. 生成对比说明，并标注任何缺失或不可比条件。

评测不仅检查最终文本，还应检查是否误选能力、是否重复调用、是否绕过校验，以及并行失败时能否给出部分结果的清晰边界。

## 常见追问

### Plan Cache 会不会返回过期数据？

计划缓存不保存业务结果，只保存经过版本约束的执行方案。实际数据仍实时查询；同时要在 Registry 或权限规则变化时使计划失效。

### 是否所有问题都应该先调用 Planner？

不需要。明确拒答、固定导航和单一确定性能力可以直接路由。Planner 应服务于存在语义选择或任务分解的请求，而不是成为所有请求的额外税。

### 多个工具能否一律并行？

不能。只有输入相互独立、权限与资源预算允许时才能并行。后一步依赖前一步结果，或多个调用可能造成资源竞争时，应保留顺序和并发上限。
