## 问题背景

企业微信经营看板里有一张「批次明细」子表。它的写法是：**当期数据全量写入，往期数据按「本期数据」标记位区分**，上层「总览指标」用 Σ 公式统计满足「本期数据 = 是」的行。

这是一套很常见的增量同步形态——不删历史，只切标记。但它有一个隐含前提：**每一行都必须被正确地翻过标记**。一旦某一行既没有被删除、也没有被标成往期，它就会永远留在汇总里。

## 现象：每一项都恰好差 1

某次把看板同步从空跑（`--dry-run`）改为真正写入后，首次真跑四个写入脚本**全部返回 0**，但第 8 步自检报 **81/91**，10 项差异：

```text
批次明细行数        166 / 165
Σ在库案件数     136,188 / 136,187
Σ已覆盖          93,697 / 93,696
Σ长期未跟进       15,230 / 15,229
Σ批次层户数       77,327 / 77,326
```

差异的形态很有意思：**每一项都恰好差 1**。这极易被当成浮点误差或口径细节放过。

定位到的线上多出来的那一行，键是一个已经不在源里的批次，`在库案件数 = 1`，但「本期数据」仍然是**是**。也就是说：这是一个**上一期存在、这一期已从源里消失**的批次，它没被标成往期，于是被批次层 Σ 公式一直计入。

> 值得强调：这**不是数据异常，而是完全合法的业务变化**。批次本来就会从源里消失。所以只要发生一次，那行就永久虚增 Σ，自检就永久报红。

## 根因：一个"看着更严格、实际少判一项"的守卫

同步脚本里有一条快路径守卫，本意是「如果没变化就跳过整个重写」：

```python
# 旧写法
if len(matched) == len(keys) == len(rows) and not same_period_stale:
    return  # 认为全部命中，直接走快路径
```

问题出在三个数的含义：`matched`（键命中数）、`keys` / `rows`（本期行数）**都是"本期维度"的数**。当线上 166 行、本期 165 行时，它们**依然全是 165**。

于是快路径被判定为「全部命中」走掉，而**增量收集到的 `older`（那一行往期孤儿）被整段跳过**——既不删、也不标「本期数据 = 否」。

## 修法：把"线上总行数"和"待处理往期行"一起纳入判据

```python
# 新写法
if (len(matched) == len(keys) == len(rows) == len(existing)
        and not same_period_stale and not older):
    return
```

两处补强：

1. 判据里补上 `len(existing)`——**线上总行数**，这是唯一能发现"多出来一行"的数。
2. 判据里补上 `not older`——明确要求**没有待标否的往期行**，把"该翻的标记翻完了"变成走快路径的前提。

修复后重跑，日志出现「往期 1 行标为 本期数据=否」，总览指标 Σ 校验全部回到 `[OK]`，完整自检 **91/91、退出码 0**。

## 三个可复用的结论

### 1. 空跑证明不了"写得对"

`--dry-run` 会把**写入侧的清理逻辑整段跳过**。它能证明"能读出数"，不能证明"写得对"。一条被长期空跑掩盖的清理缺陷，只有在真正写入时才会暴露——而它表现为**自检差 1**，最容易被放过。

所以：**切换到真写入的第一轮，必须按完整批次观察，并把自检差异当成缺陷而不是误差。**

### 2. 守卫条件里的每个变量都要能发现"多"

守卫是用来发现异常的，所以判据里必须至少有一个**能发现"多出来"的数**。上面旧写法的三个数全是"本期维度"，天然只会发现"少"，发现不了"多"。

同类排查方法：把守卫里每个变量的取值域写出来，看是否存在"异常发生时它不变"的情况。

### 3. 差异为 1 时先怀疑"孤儿"，不要先怀疑精度

整数型汇总差 1，几乎总能定位到某张表多一行/少一行。排查顺序建议：

1. 先比**行数**，再比金额/比率；
2. 行数不等时，按**业务键做外连接**，找出单侧独有行；
3. 对独有行，回溯它是**本期新增**、**已从源消失**，还是**键被改动**；
4. 把"已从源消失"这类行纳入**每轮必须处理**的清单，而不是留给下一轮的全量重写。

## 落回数据治理

这件事的核心不是某个 `if` 写错了，而是**生命周期状态没有被当作一等公民**：

- 每一行都需要明确它属于「当期」还是「往期」；
- **翻标记必须和写入同批完成**，不能依赖下一次全量兜底；
- 自检要覆盖「Σ 与明细一致」这类**跨层一致性**，而不只是行内字段合法性；
- 差异出现时，先归因到具体行，再判断是业务变化还是缺陷。
