## 问题：如何判断一次工具调用是“好的”

只看工具有没有返回成功并不够。Agent 可能选错工具却恰好得到结果，也可能选对工具但参数范围错误，最终给出看似合理的答案。

工具调用质量至少包含三层判断：该不该调用、调用参数是否正确、执行结果是否真正解决用户问题。只有把链路拆开，才能知道问题来自路由、参数理解、执行能力还是结果表达。

## 核心结论：分层衡量，不用单一成功率

推荐将核心指标拆成五组：

| 层级 | 关键问题 | 示例指标 |
|---|---|---|
| 工具选择 | 是否选择了正确能力，是否漏选或多选 | 选择准确率、召回率、拒答准确率 |
| 参数提取 | 指标、维度、时间与过滤条件是否正确 | 字段级准确率、完整匹配率 |
| 执行结果 | 工具是否安全完成并返回可验证结果 | 执行成功率、结果一致性 |
| 调用效率 | 是否存在重复、无效或过长的调用链 | 平均调用次数、重试率、延迟 |
| 端到端体验 | 最终回答是否解决用户问题 | 任务成功率、澄清率、人工接管率 |

单一“调用成功率”会掩盖很多问题。例如执行接口返回 200，并不代表 Agent 选对了指标；一次澄清也不一定是失败，它可能是避免错误回答的正确决策。

## 如何设计离线评测集

每条样本不只保存自然语言问题，还要保存可验证的期望行为：

- 期望调用或拒答的能力标识。
- 必填参数、允许的参数变体和不可出现的参数。
- 是否应该澄清，以及缺少的关键信息。
- 可接受的调用顺序和最大调用次数。
- 对执行结果的结构化断言，而非固定自然语言答案。

问题集应同时覆盖标准表达、口语别名、上下文追问、歧义问题、无权限请求、越界请求和无法回答的问题。真实线上样本可以进入评测集，但必须先移除身份、业务对象和结果数据。

## 四层证据不能互相替代

工具调用系统常见的误区，是用某一层的高分宣布“已经可以上线”。更稳妥的做法是把证据拆成四层：

| 证据层 | 主要回答 | 不能证明 |
|---|---|---|
| 离线检索与路由 | 候选是否覆盖、排序是否改善 | 参数、权限和真实执行正确 |
| 确定性协议回放 | 关键决策、拒绝、回退和结构化输出是否符合契约 | 真实模型表达质量 |
| 全量自动化回归 | 代码、Registry、MCP 和运行边界是否发生工程回归 | 真实问题分布和业务接受度 |
| 受控 Pilot | 真实表达、延迟、错误类型和恢复是否达到放量 Gate | 长期规模化运行稳定性 |

例如，确定性回放 20/20 说明被冻结的协议与决策样本全部符合断言；它不等于真实模型准确率 100%。同样，数百项自动化测试通过也不能替代真实用户样本和人工复核。

高风险 case 应优先使用结构化断言：能力标识、参数、权限决策、是否执行、错误类型、回退路径和敏感信息扫描。自然语言表达可以另设 Judge 或人工评审，但不应覆盖已经失败的确定性安全断言。

## 参数评测为什么要拆字段

参数通常不是一个整体字符串。指标识别正确，不代表时间范围、维度或过滤条件也正确。可以先逐字段比较，再计算整条调用的完整匹配：

1. **能力标识**：是否调用正确的工具或指标。
2. **时间范围**：相对时间是否被转换为正确边界。
3. **维度与过滤**：是否选择已注册维度，值是否通过映射。
4. **权限上下文**：是否只来自可信系统输入。
5. **输出约束**：结果规模、排序和导出请求是否符合规则。

字段级结果更适合定位改进方向：能力标识错误通常指向检索和路由，时间错误指向解析规则，权限错误则属于安全缺陷，不能仅靠调 Prompt 解决。

## 线上监控看什么

离线评测回答“发布前是否达到预期”，线上监控回答“真实使用中是否持续可靠”。建议观察：

- 各能力的调用量、成功率、拒绝率和澄清率。
- 校验失败、超时、空结果和重复调用的分布。
- 每类问题的调用步数、端到端延迟与资源消耗。
- Registry 或 Prompt 版本变化前后的指标差异。
- 用户纠正、重新提问和人工接管信号。
- 真实样本覆盖是否达到预设场景分布，是否出现不可接受的关键错误。
- 检索节点与端到端尾延迟是否同时满足预算，而不只看平均值。

日志应优先记录结构化标识、状态和版本，不默认保存原始敏感问题、查询结果或完整权限数据。

## 从指标进入优化闭环

发现问题后，先定位层级再选择手段：

- 工具召回不足：补充别名、示例与检索索引。
- 候选过多：改善元数据描述、过滤条件和澄清策略。
- 参数错误：收紧 Schema，增加确定性解析与边界样本。
- 重复调用：检查状态复用、终止条件与查询计划缓存。
- 执行成功但任务失败：补充结果校验与回答层评测。

每次修复都应把失败样本匿名化后加入回归集，避免同类问题在下一次 Registry、模型或工作流更新中重新出现。

对于准备放量的变更，还应预先冻结 Gate：最小有效样本量、必须覆盖的场景、关键错误上限、尾延迟预算、回滚条件和独立评审人。没有达到 Gate 时继续收集证据，而不是因为开发周期结束就改变阈值。

## 常见追问

### 工具选择准确率达到多少才算好？

没有脱离场景的统一阈值。高风险能力更应关注误调用率和拒答正确性；高频低风险能力可以同时优化召回与效率。阈值应按能力风险分层，并以稳定回归趋势为主。

### 澄清率越低越好吗？

不是。对信息不足的问题主动澄清是正确行为。需要关注的是“不必要澄清”和“应该澄清却直接执行”，而不是简单追求更低比例。

### 能否用模型给模型打分？

可以把模型评审作为辅助信号，尤其用于回答完整性和表达质量；工具标识、参数、权限和执行结果应尽量使用确定性断言。高风险样本仍需要人工抽检。
