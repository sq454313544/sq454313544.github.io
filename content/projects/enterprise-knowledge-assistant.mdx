## 我的工作

- **基于开源定制**：在开源项目 WeKnora 的基础上定制员工问答页与管理员发布界面，独立部署并维护上游补丁清单，明确区分上游能力与本人定制范围。
- **资料发布与版本治理**：建立原文版本、发布批次、撤回与新版替代机制；回答只从允许使用的已发布资料生成依据，资料发布变化后旧会话转为只读并提示「依据已更新」。
- **回答依据与出处**：回答按已发布资料给出结构化出处，条件不足时先给出有依据的候选并注明适用范围；引用可定位到来源，不等于已完成完整原文阅读闭环。
- **身份集成**：对接作业系统一次性票据单点登录，完成核心登录链路与回调重放场景的真实验证，并禁止外部账号使用本地密码登录。

三条设计原则：

1. **依据只来自已发布批次**：检索侧按当前批次过滤，撤回的资料立即不再作为依据；
2. **批次推进是原子的**：发布走「取锁 → 维护窗口 → 一个事务写批次与指针 → 清缓存」，业务拒绝时不强行退出维护态；
3. **上游能力与定制分开记账**：每一处上游改动都有编号、原因、证据、回退方式与升级影响。

## 工程重点

### 资料治理：发布之后的部分

知识库里最容易被低估的是**发布之后**的部分。制度文件会改版，改版之后旧回答还算不算数？这里的处理方式：

| 场景 | 机制 |
|---|---|
| 资料改版 | 登记新的原文版本，发布时按批次推进，旧版标注为被替代 |
| 资料撤回 | 撤回后检索侧立即过滤，员工侧返回「已撤回」且不返回正文 |
| 旧会话 | 依据批次变化后旧会话转为只读，提示「依据已更新」，需按最新资料重新提问 |
| 发布中的并发 | 发布锁（事务内 `FOR UPDATE`，跨进程）+ 在途问答等待窗口，避免半次切换 |
| 草稿 | AI 按勾选来源起草，管理员修改并确认后才发布；起草本身不落库、不推进批次 |

一个关键判断是**旧会话不携带旧答案继续回答**。保留旧答案会让员工拿到一份"当时正确、现在可能错"的结论，而界面上无法体现这个时间差。改成只读并明确提示，比悄悄给一个过期答案更负责。

### 回答的四种终态

「有文字」不等于「回答成功」。系统把每条回答归入明确终态，界面按终态呈现：

- 正常有依据；
- 无依据（资料里没有 → 回固定话术，不编造）；
- 条件不足（资料按适用范围分成多组而提问没说明条件 → 给最多 3 个候选，各带自己的适用范围与出处）;
- 取消或失败。

候选是这套设计里最有价值的部分。内部制度常常"分人群不同规定"（例如按职级、按部门），传统问答会随便挑一条回答，员工无从判断是否适用于自己。所以当检索证据横跨多个适用范围时，系统**不收敛成单一答案**，而是把条件列出来让员工自己认领。

### 身份集成：一次性票据

员工身份复用现有作业系统账号，采用**一次性票据**方案：登录入口跳转到作业系统授权页 → 回跳我方回调 → 用一次性 code 立刻换取身份 → 查询账号权威状态（读不到就不放行）→ 建立/取出本地用户 → 回跳只带一次性票据、令牌不进 URL。

端到端 3.0～5.2 秒。两处值得记录的细节：

- **入口必须与登记的回调地址同源**。从另一个主机名发起会因跨来源丢失 nonce Cookie 而报状态校验失败——这是配置前提，不是产品缺陷；
- **一次性票据不能重试同一个 code**。换取失败就重新走登录，而不是重放。

## 一个值得追问的取舍：能用代码确定的边界，不要交给配置或模型

两处边界是在实测中被发现的：

- **联网检索曾经由客户端开关决定**。实测请求带开关时服务端确实会去联网。这属于部署边界漏到了客户端，改成部署级总闸，客户端与智能体配置只算"申请"，配置缺失时失败关闭。
- **无依据时的兜底由智能体配置决定**。证据被过滤清空时，模型自己写了一段说明而不是回固定话术。这同样不可接受——**"材料里没有"必须是确定性的，不是模型的选择**。

这两处的共同点是：**能用代码确定的边界，不要交给配置或模型去"应该会遵守"。**

## 我的职责边界

我负责定制范围判断、发布与撤回治理设计、问答链路调整、身份集成和运行验证。开源项目本身的能力不计为本人成果；与智能问数助手共用同一代码仓库不等于合并部署，也未接入数仓。

## 复盘

做企业内部知识库，工程难点不在"接一个大模型"，而在三件事：

1. **依据的边界**：哪些资料可以用、用到什么版本、撤回之后怎么办；
2. **不确定性的呈现**：条件不足时给候选而不是硬答，无依据时明确说没有；
3. **边界的落点**：能写成部署级开关的，不要留给客户端开关或模型自律。

这三件事都没有漂亮的演示效果，但它们决定员工会不会真的信任这个入口。
