## 项目背景

当业务人员需要获取指标或明细时，往往需要在多个系统、口径说明和人工取数之间反复确认。这个项目的目标不是让模型直接访问数据，而是建立一条可解释、可校验、可审计的自然语言问数链路。

## 目标与边界

- 支持指标查询、受控明细查询、指标解释、上下文追问和结果导出。
- 通过企业微信和 Web 双入口提供流式响应，并保持一致的查询与权限边界。
- 将指标定义、可用维度和查询模板收敛为可维护的 Registry。
- 让 Agent 负责理解、路由与解释；让受控执行层负责校验、查询和导出。
- 不向公开站点披露业务名称、数据对象、账号、原始 SQL 或真实查询结果。

## 核心设计

## 我的职责

我负责产品设计、架构设计与核心开发，将业务侧的自然语言取数需求拆解为可验证的产品与工程边界：定义可查询能力、梳理指标与元数据入口，并将路由、校验、权限、流式响应、结果导出和审计串成可维护的交付链路。公开案例只保留抽象架构与脱敏指标，不暴露数据库对象或真实查询结果。

### Registry First

将指标口径、允许维度、明细映射与查询模板纳入统一注册表。每个问题先定位可用能力，再进入受控执行，避免仅靠 Prompt 推断业务含义。

### 受控查询边界

- 使用只读权限与参数校验约束查询入口。
- 通过 AST 校验、白名单、危险语句拦截和返回量限制控制风险。
- 在执行前注入权限范围，在执行后保留审计信息。
- 将文件导出从 Agent 编排中拆出，由独立能力处理鉴权与结果交付。

### 可追问的结果解释

会话上下文保留问题、已选指标和已返回结果的必要摘要；追问仍需经过能力匹配与校验，不复用未经确认的查询计划。

## 迭代过程与决策

第一版检索在离线样本上存在召回不足的问题，因此没有继续依赖更长的提示词，而是补充候选召回与重排序，并把 51 条离线评估集作为每次调整的共同基准。系统也没有让模型直接生成并执行原始 SQL：这会放大口径漂移、越权访问和不可审计的风险。最终保留由 Agent 负责理解与解释、由受控执行层负责校验与查询的分工；直接执行与未经校验的计划都被排除在公开方案之外。

## 验证与当前状态

- 使用 51 条离线评估集验证意图路由与候选检索。
- 检索 Recall 从 39.22% 提升至 82.35%，MRR 从 0.412 提升至 0.833。
- 全量自动化测试达到 246 项通过，覆盖关键路由、校验、并发与失败降级。
- 完善版本化元数据、请求追踪、查询预算、消息去重、并发与慢查询监控。
- 已完成测试环境端到端验收，并持续进行稳定性与性能加固。

## 复盘

智能问数的稳定性不来自“更长的 Prompt”，而来自可维护的口径注册、确定性查询边界和可回溯的验证流程。后续迭代会继续围绕评测覆盖、能力变更和异常降级完善工程质量。
