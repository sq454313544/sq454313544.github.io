## 建设目标

- 把分散在业务库、补充表和外部系统的数据接入统一链路，替代人工导出与各自直连。
- 将源数据接入、标准化、核心建模、应用汇总和质量治理组织为可重复运行的链路。
- 对高频变化且具备可靠水位条件的数据采用增量，对不适合增量的数据保留全量策略。
- 用业务口径注册表和指标、维度、明细契约约束看板、报表与智能问数的消费口径。
- 让失败批次停止在发布门之前，避免下游读取不完整或未经验证的数据。
- 不公开内部库表、字段、连接配置、业务映射或原始数据。

主消费链路以 `raw → stg → core → ads` 为主，DWS 只为明确的明细分析或固定聚合需求按需建设。这样既保留分层职责，也避免为了“层级完整”维护没有消费者的重复汇总。

采集侧按来源编排：业务库走 DataX 受控同步，外部系统与在线表单走独立的自动采集链，多路采集合并到一个调度 DAG、按来源分任务链执行，任一来源失败不阻塞其他来源。

## 工程重点

### 分层模型与数据资产

通过 DataX 同步 102 张可用表，使用 dbt 建设标准化、核心事实与维度、应用汇总和按需宽表，形成接近 300 张表 / 视图的数据资产。经营看板、报表和智能问数优先消费经过治理的核心层与应用层，不再直接依赖来源表。

### 多源采集与统一调度

- 外部来源包括工作手机系统、外呼系统与在线回款表单，统一为“采集 → 落表 → 校验 → 入库 → 调度”的链路，替代人工下载与手工整理。
- 采集任务合并到一个调度 DAG、按来源分任务链，抓取与入库脚本保持独立，只替换调度外壳。
- 逐格校验替代抽样检查：按源的列集、非空率与行数环比做断言，少列或少行即中止。
- 跨源人员与坐席映射统一以人事名单为准，不按坐席串截取姓名；同一份数据的多种载体不重复建源。

### 刷新策略与发布门

- 每日全量链路负责完整校准；增量链路按双游标方案实现，用于缩短高频变化数据的可用等待时间。
- 全量与增量任务在入口互斥，避免原子换表、增量合并和 dbt 构建相互覆盖。
- 增量批次只有在抽取、校验和合并全部成功后才提交水位；没有变化时跳过不必要的下游构建。
- dbt 测试、中文注释、数据新鲜度和发布检查共同组成下游可见前的质量门。
- **当前运行策略**：因源库业务字段变化不会自动推进更新时间字段，日常刷新统一走全量；增量链路保留，待来源具备可靠水位条件后恢复。这一取舍见下文。

### 权威契约与渐进治理

业务口径注册表作为收集与确认入口，指标、维度和明细契约作为消费边界。新增需求先确认定义和来源，再派生到下游模型与助手运行时 Registry；未确认项进入待确认清单，不直接污染正式口径。

### 运行环境（区分历史与当前）

- **历史阶段**：已完成服务器运行环境部署和下游数据源切换，作为阶段性交付留档。
- **当前阶段**：数仓只在本机环境运行与验收，日常刷新走全量；开发在本地分支完成验证后再合并，不经过服务器部署。
- 不把“环境曾部署”表述为当前仍在服务器运行，也不把历史阶段的能力说成已经长期验证的稳定生产结论。

<h3 id="wecom-dashboards" className="scroll-mt-24">企业微信经营看板</h3>

三条经营看板基于**企业微信智能表格**交付，把原先“人工导出 → 手工整理 → 手工贴表”的过程替换为自动采集、指标汇总与定时同步。

- **立案与回款趋势｜生产使用**：按日粒度建模、周月用汇总表达，按项目与批次两级分组，覆盖立案与回款口径；定时同步运行中，并做过整表逐键对账。
- **项目维度过程指标监控｜生产使用**：项目、批次与人员的过程指标，把人工导出替换为自动采集与汇总；换源切换已完成，自检项目全部通过。
- **人员过程数据追踪｜数据已上线**：通话、工作手机、回款等多来源人日聚合，含人员映射与历史沉淀；定时任务已启用，验收与正式切换仍在收尾。

三条线的共同实现：

- **自动采集替代人工导出**：来源系统与在线表单由采集链负责下载与入库，人工只保留例外处理。
- **指标汇总与定时同步**：汇总与人日粒度写入智能表格，按调度时刻分班次运行，避免与数仓整表重建窗口重叠。
- **依赖预检**：执行前确认数据库可往返、当日采集已落盘，条件不满足则带明确退出码失败，不静默跑空。
- **数据生命周期**：区分本期数据与往期数据，及时标记已从源端消失的行，避免汇总公式长期虚增。
- **回读对账与失败告警**：同步后按定位信息回读校验，任务失败自动推送告警而不是等人工翻同步状态表。
- **隐私边界**：智能表格侧只放汇总与人日粒度，不放客户级隐私字段。

仍待完善的边界：人员维度看板的验收与正式切换尚未关闭，部分口径说明按业务决定保持空表，图表筛选与当前周期需要在有数据后按数值核对。同步脚本的重跑与对账仍在持续进行，不把三条线都表述为已完成正式验收。

<h3 id="report-automation" className="scroll-mt-24">业务报表与自动化</h3>

周报、月报、运营日报和日常业务取数并入同一条交付链路，工作分三层：

- **口径维护**：每个报表结果集都有对应的业务口径与统计截止日说明；源库版与数仓版并存时，对差异逐项归因，不做“看起来一样”的默认假设。
- **取数交付**：报表 SQL 在数仓环境执行并导出结果集，业务侧继续用人工执行作为回退通道，不把候选视图写成已替换日常入口。
- **周报自动填表**：把周报 SQL 的结果集自动灌入周会报告 Word 模板，替代原先“跑 SQL → 看结果 → 一格格贴”的过程。流程为「结果集导出 → 按模板保真写入 → 结构校验 → 逐格对账 → 用 Word 真实打开复验」，三条校验全部通过才算这一次填表可用；表头、列宽与箭头配色规则按原文档反向标定，手写分析段落保留给业务填写。

## 一个值得追问的取舍：为什么现在日常走全量

增量刷新看起来总是更快，但它有前提：主键、更新时间和删除语义必须可靠。

实际核对发现，源库的业务字段变化不会自动推进更新时间字段。这意味着按更新时间抽增量会**静默漏掉已变更的行**——数据看起来刷新成功了，内容却是旧的。这类错误不会让任务失败，也不会出现在行数校验里。

因此当时的判断是：

- 把增量链路**保留在代码里**（双游标设计、水位提交规则、与全量的入口互斥都已实现），作为来源具备可靠水位条件后的恢复路径；
- 日常刷新**统一走全量**：用可接受的刷新耗时换取“数据确实是最新的”；
- 在数据新鲜度状态里如实反映刷新方式，让下游知道读到的是哪一种批次。

同类取舍还有两个：**DWS 改为按需建设**（固定建设大量日汇总宽表会复制口径并增加维护成本，现在只让核心事实与应用汇总承担主消费），以及**报表保留人工执行通道**（自动出报工具链完成重新基线化之前，保留可交付通道比让业务等待一个未验证的自动流程更稳妥）。

## 可公开成果

- 通过 DataX 同步 102 张可用表，使用 dbt 形成接近 300 张表 / 视图的数据资产，并让 DWS 从固定层收敛为按需建设。
- 建立多源采集与统一调度链路，把人工导出替换为自动采集，并补充逐格校验与行数环比看门狗。
- 建立全量与增量协同刷新机制：水位提交规则、任务互斥和发布门，并明确当前采用全量刷新的原因。
- 建立业务口径注册表、数据字典、枚举规范、数据契约、质量检查与运行健康机制。
- 交付企业微信经营看板三条线、周月报与业务取数，以及周报结果集到 Word 模板的自动填表与逐格对账。
- 完成过服务器运行环境与下游数据源切换（历史阶段，当前在本机环境运行）。

> 案例中出现的规模、自检项数与链路描述来自授权范围内的公开资料与实施记录，均为阶段性结果，不代表长期稳定能力。

## 为什么看板同步要排在数仓整班之后

看板读取的是会在整班中被重建的表。同步时刻必须排在重建与校验之后，否则会读到重建中的中间态。这个约束由调度时刻与依赖预检共同保证，而不是靠经验记住。

## 当前状态与边界

项目处于持续维护和运行加固阶段，在本机环境运行与验收。规模数据按 2026-09 快照口径表达；刷新窗口、内部对象、运行地址、账号、原始 SQL 和业务数据不进入公开站点。企业微信经营看板的三条线分别处于生产使用与验收收尾阶段，业务报表暂保留人工执行通道；后续成果只在完成核验后更新，不把规划或单次测试结果写成稳定能力。

## 复盘

数据仓库的价值不只是“把数据搬进新库”，而是让接入、口径、质量、发布和消费边界可以持续演进。真正的工程难点从首次建模转向长期运行：既要缩短数据等待时间，也要确保每次刷新、契约变化和下游切换都可验证、可回退。
